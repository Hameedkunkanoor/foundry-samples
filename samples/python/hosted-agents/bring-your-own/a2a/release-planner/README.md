# What this sample demonstrates

Three LLM-backed native A2A agents collaborate on a release plan:

1. A **coordinator** delegates the request to a **scope specialist**.
2. It sends the original request and scope assessment to an independent
   **risk reviewer**.
3. It uses both assessments to synthesize a release plan with another model call.

The coordinator returns the plan and evidence from both remote completed Tasks.
It does not replace failed delegation with a model-only answer.
These are planning recommendations, not executed changes or release approvals.

## How it works

```text
User -> native A2A coordinator
          |-> native A2A scope agent -> Foundry model
          |<- completed Task + scope assessment
          |-> native A2A risk agent -> Foundry model
          |<- completed Task + risk assessment
          |-> Foundry model -> consolidated plan
        <- completed Task + plan + both remote Task IDs
```

All three azd services share [one runtime](src/release-planner-a2a/main.py).
`AGENT_ROLE` selects their behavior. The native A2A SDK owns Tasks and artifacts;
`azure-ai-agentserver-a2a` hosts the executor and selects caller-isolated
Foundry Task storage when hosted.

The configured specialist endpoints are discovery starting points. The
coordinator fetches each Card, checks its skill, selects the first advertised
JSONRPC / A2A 1.0 interface, and sends `SendMessage` to **that interface's URL**.
The advertised URL must satisfy the same project/loopback trust checks and
cannot change between HTTP and HTTPS. A missing compatible interface or unsafe
URL fails before invocation; there is no fallback to the configured endpoint.
If the Card omits Foundry's `api-version` query, the configured value is retained.

The coordinator verifies completed state, role, run ID and the input
digest in the returned artifact. Task/execution IDs are generated by the remote
agent, not by the model. The scope assessment is input to the risk review; both
become input to synthesis.

The model uses the project's Responses endpoint with managed credentials and
the current platform call context. This is a model call, not a Responses-agent
substitute for the native A2A delegation.
Hosted outbound A2A explicitly selects the agent instance's managed identity
using `FOUNDRY_AGENT_INSTANCE_CLIENT_ID`; it does not rely on an unspecified
default identity. Model calls retain the ordinary default credential.

Follow the shared [Python startup configuration](../../../README.md#python-startup-configuration).

## Prerequisites

1. Python **3.13**, uv **0.11.7 or later**, azd **1.37.2** and agent extension
   **1.0.0-beta.23** are the tested toolchain.
2. An existing Foundry project enabled for native A2A and managed Task storage.
3. An existing **`gpt-5-nano`** model deployment. The request uses minimal
   reasoning effort; a different model must support that setting.
4. Permission to deploy/invoke agents and use that model.
5. The **coordinator's agent identity** needs **Foundry Agent Consumer** or
   higher on the target project for outbound A2A calls. Deployment alone does
   not grant that access. Ask the project owner to grant only required access.

Three agents, sessions and three model calls per successful plan incur charges.
Use synthetic requests, do not include sensitive data, and do not load test.
The sample only permits specialist endpoints in the configured Foundry project,
or loopback HTTP when running locally. It never forwards an incoming user token.

The runtime uses the same explicit alpha sources as the introductory samples:
A2A `1.0.0a20261029006`, Core `2.3.1a20261029006` and native A2A `1.2.3`.
Keep the committed project and lock. The repository's alpha-feed policy gate
still applies; no policy bypass is added.

## Option 1: Azure Developer CLI (`azd`)

### Install and sign in

Update the installed extension, or replace `update` with `install`:

```powershell
azd extension update azure.ai.agents --version 1.0.0-beta.23 --source azd
azd auth login
$env:AZD_ALPHA_ENABLE_AGENTS_A2A = "true"
```

### Initialize the agent project

From a fresh directory, adopt the **local manifest from your checkout of this
PR**. Replace both absolute paths/project ID:

```powershell
azd ai agent init --src . -t "C:\path\to\release-planner\azure.yaml" `
    --project-id "<EXISTING-PROJECT-ARM-ID>"
```

The manifest has three agent services; do not use a single `--agent-name`
override. Open the adopted `azure.yaml` and change these **three `name` fields**
before deployment, for example:

| Service key, unchanged | Example unique `name` |
|---|---|
| `scope` | `release-scope-youralias-01` |
| `risk` | `release-risk-youralias-01` |
| `coordinator` | `release-coordinator-youralias-01` |

Keep the service keys, shared source path, protocol declaration and role
environment values unchanged.

### Configure the existing model

```powershell
azd env set AZURE_AI_MODEL_DEPLOYMENT_NAME gpt-5-nano
```

Skip model provisioning. Do not run `azd up` or `azd provision` against a shared
project; this sample uses existing infrastructure.

### Deploy the specialists

```powershell
azd deploy scope
azd deploy risk
azd ai agent show scope --output json
azd ai agent show risk --output json
```

Confirm both are active. Copy each `agent_endpoints.a2a` URL:

```powershell
azd env set SCOPE_AGENT_ENDPOINT "<SCOPE-A2A-ENDPOINT>"
azd env set RISK_AGENT_ENDPOINT "<RISK-A2A-ENDPOINT>"
azd deploy coordinator
azd ai agent show coordinator --output json
```

Endpoint values must match the unique names you deployed. Pass the native A2A
URLs, not model endpoints, Responses-agent endpoints, or Card URLs.

### Authorize the coordinator

Copy `instance_identity.principal_id` from the coordinator's status. Ask the
project owner to grant this new identity **Foundry Agent Consumer** on the
target project using the normal access process. Do not grant unrelated roles,
remove existing assignments or disable isolation.

**Current hosted validation blocker:** the approved test project rejected the
requested minimal grant with `RoleAssignmentLimitExceeded`. No role was created.
The fully hosted coordinator's outbound Card request returned 404, while the
signed-in user could access the same Card. Until the role prerequisite and
service access are resolved, do not claim a fully hosted end-to-end pass.

### Invoke the deployed coordinator

After access is confirmed, replace the example name/version with the
coordinator's deployed name/version:

```powershell
azd ai agent invoke release-coordinator-youralias-01 -p a2a --a2a-version 1.0 `
    --version 1 --new-session --output raw `
    "Plan a staged release of search filters for 20 internal testers. Include tests and rollback. Budget is undecided."
```

Expected completed Task artifact is a JSON object containing:

- `delegation_verified: true`;
- a model-generated `plan`;
- two `delegations`, with roles `scope` and `risk`;
- a nonempty analysis, distinct remote `task_id` and `execution_id` for each;
- a matching `run_id` and request digest verified by the coordinator.

Inspect the JSON-RPC body even for HTTP 200. An operation error, absent evidence,
incomplete model response or failed specialist is not success.
Do not judge success by fixed model prose: wording is nondeterministic.

## Using the managed A2A tool and Toolbox

The direct native workflow above uses **no Toolbox**. The managed alternative is:

```text
LLM caller -> Foundry Toolbox MCP endpoint
           -> A2A tool -> RemoteA2A project connection -> specialist A2A endpoint
```

The [official A2A tool documentation](https://learn.microsoft.com/azure/foundry/agents/how-to/tools/agent-to-agent?pivots=python)
describes two Python surfaces:

- Prompt agent: `A2ATool(a2a_version=A2AProtocolVersion.V1_0,
  project_connection_id=connection.id)`.
- Hosted caller: add `A2AToolboxTool` to a Toolbox, then attach that Toolbox's
  MCP endpoint with Agent Framework `FoundryToolbox`.

To reuse these specialists:

1. Create a **RemoteA2A** project connection per specialist in the Foundry
   portal/Toolkit. Target its A2A base URL and audience `https://ai.azure.com`.
2. Use calling-agent identity for app-only calls, or the documented
   `UserEntraToken` compatibility path where delegated user context is required.
   `AgentOnBehalfOfUser` has additional blueprint/token/consent requirements;
   it is not interchangeable with the other authentication types.
3. Add both A2A connections as named tools to a Toolbox and publish its intended
   default version. For Foundry targets, current docs resolve the Card path
   automatically; do not copy older samples' forced v0.3 Card path.
4. Attach the Toolbox MCP endpoint to an LLM caller. Require specialist calls
   and verify actual tool invocations rather than trusting a plausible answer.

This centralizes credentials, policy and discovery instead of maintaining the
direct client. It is not automatically used just because an agent exposes A2A.
No A2A connections or Toolboxes existed in the validation project, and this
task did not create or execution-test a managed Toolbox integration. It is a
separate follow-up, not a workaround claimed to bypass the current role limit.

## Troubleshooting

- **Model response incomplete:** fail explicitly; do not synthesize from partial
  output. Keep the bounded prompts and compatible model/reasoning setting.
- **Card works for you but not the hosted coordinator:** inspect its identity
  access and target subscription enablement. Do not forward your token.
- **`RoleAssignmentLimitExceeded`:** ask the project/subscription owner to resolve
  quota/access. Do not delete arbitrary existing assignments.
- **Specialist error or missing evidence:** the overall request must fail.
  Inspect `A2A_RELEASE_FAILED`, the role and correlated Task/trace IDs.
- **Endpoint rejected:** both discovery and advertised URLs must pass the
  same-project/loopback checks without switching transport. A Card cannot
  redirect authenticated calls to another project or external host.
- **No compatible interface:** the Card must advertise a JSONRPC A2A 1.0 URL;
  update the agent's Card rather than bypassing discovery.
- **Download/TLS failures:** preserve dependency pins and fix approved network,
  proxy or certificate configuration; do not disable TLS verification.
